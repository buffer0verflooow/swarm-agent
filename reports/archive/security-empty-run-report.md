# 安全性虚Run问题 — 报告

**报告人**: reporter (蜂群 Worker)
**日期**: 2026-07-18
**来源**: analyst-01 分析结果 (run f4b6d21f)
**状态**: 已确认 (confirmed)

---

## 1. 概述

安全探索产品线的经营账本中存在「虚Run」记录。这些 Run 在 Router 层被登记为运行中/已完成状态，但实际未消耗任何 LLM 资源、未产生任何产出物、未关联任何 Worker Session。其存在污染了产品线的运行统计和成本核算。

---

## 2. 已验证证据

### 2.1 虚Run 的识别特征（与正常Run对比）

| 维度 | 正常Run | 虚Run |
|------|---------|-------|
| status | completed | **empty_run** |
| token.direct | >0 | **0** |
| token.input | >0 | **0** |
| token.output | >0 | **0** |
| token.cache | ≥0 | **0** |
| token.reasoning | ≥0 | **0** |
| model | 有具体模型名 | **空字符串 ""** |
| worker_session_id | 有效 session ID | **空字符串 ""** |
| output_bytes | >0 | **0** |
| artifacts | 有产物文件 | **空数组 []** |
| 耗时 | 与任务规模匹配 | **48,000–53,000 秒**（约 13–15 小时） |

### 2.2 关键结论

- **全零 Token 消耗**：所有五个 token 维度（direct/input/output/cache/reasoning）均为 0，排除任何实际 LLM 调用。
- **异常长耗时**：虚Run 的 elapsed 字段为 48K–53K 秒（13–15小时），远超正常任务，且与实际资源消耗 0 形成矛盾。
- **零产出**：output_bytes=0，artifacts 为空数组，无任何交付物。
- **无 Session 关联**：worker_session_id 为空，无法追溯到任何 Worker 进程。

### 2.3 可信度评估

- ✅ **高可信度**：所有识别特征均来自账本中的结构化字段（status/model/worker_session_id/token.*/artifacts/output_bytes），属于同一数据源的内部一致性验证，不是推理推断。
- ⚠️ **待确认**：虚Run 的产生根因（Race condition？Router 重试逻辑？Worker 崩溃后未清理？定时器触发空执行？）尚未通过代码级审查或复现实验确认。

## 3. 影响分析

| 影响领域 | 严重程度 | 说明 |
|----------|---------|------|
| **成本核算失真** | 中 | 虚 Run 被计入运行总数，导致 Run 成功率、平均成本等指标被稀释，管理决策依赖的数据不准确。 |
| **运行监控误判** | 中 | 耗时 13–15 小时的 empty_run 条目可能触发误告警，或掩盖真正异常的 Run（因为虚Run 拉高了耗时基线）。 |
| **数据膨胀** | 低 | 每条虚Run 在账本中仅一行记录，存储成本极低，但长期积累可能影响查询性能。 |
| **安全影响** | 低 | 当前无证据表明虚Run 被恶意利用——它们是空记录，不执行代码、不消耗资源、不产生网络流量。 |

综合评定：**中等影响**，主要损害运维和统计准确性，不构成直接安全威胁。

---

## 4. 根因假设（待验证）

以下假设来自现有证据的推断，**尚未通过代码审计或实验复现**：

1. **Router 层 Race Condition**：Router 在创建 Run 记录后、分配 Worker 前异常退出或超时，导致 Run 记录残留。
2. **Worker 分配失败后未回滚**：Router 尝试分配 Worker 失败（如 Worker 池满、网络错误），但未将 Run 状态标记为 failed，而是遗留为 empty_run。
3. **定时触发空执行**：某个 Cron/Scheduler 以 empty_run 状态写入了占位记录，但后续流程未填充数据。
4. **状态机 Bug**：Run 生命周期状态机在某条路径上从 empty_run 跳过了所有执行阶段直接结束。

---

## 5. 修复建议

### 5.1 立即措施（运维层面）

1. **清理历史虚Run**：编写脚本扫描所有 status=empty_run 的记录，确认无关联数据后归档或删除。
2. **添加告警规则**：当 empty_run 数量在时间窗口内超过阈值时触发告警，防止问题扩大。

### 5.2 短期修复（代码层面）

3. **Router 原子性保证**：Run 创建与 Worker 分配应在同一事务或补偿逻辑中完成——如果 Worker 分配失败，Run 状态应立即标记为 failed/aborted。
4. **Run 创建入口校验**：在写入 Run 记录前校验必要字段（model、session_id）非空；创建阶段不允许 status=empty_run。
5. **超时清理机制**：对状态为 pending/empty_run 且超过合理时长（如 1 小时）的 Run 自动标记为 orphaned 并清理。

### 5.3 长期改进（架构层面）

6. **Run 生命周期状态机重构**：明确每个状态的进入/退出条件，禁止 empty_run 作为终态存在。
7. **可观测性增强**：为 Run 生命周期各阶段埋点（创建→分配→执行→完成/失败），便于追踪每条 Run 的完整轨迹。

## 7. 结论

虚Run 是一个**已确认的数据完整性问题**，表现为 Router 层产生了零消耗、零产出的空记录。直接影响是运维统计失真，间接影响是监控基线被污染。当前无证据表明存在安全风险或恶意利用。

建议按「5.2 短期修复」中的原子性保证和入口校验作为第一优先级，此类问题通常来自状态管理的不一致，修复成本低、见效快。
