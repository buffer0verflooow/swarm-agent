端到端工作流程

系统启动后没有固定的 discover → analyze → exploit → report 阶段锁。初始任务只是种子，后续任务由知识捕获和市场信号自然展开。

1. 提交目标swarmctl.py task submit 写入外部请求并创建 run。
2. 发布种子任务run_manager 根据 intent/profile 生成 scan/analyze/report 初始任务。
3. worker 领取角色匹配、优先级排序、原子 UPDATE，把 pending 任务转成 running。
4. executor 执行worker 把 task、KB context、model_profile 传给外部执行器。
5. capture 入库结果转为 raw event 和 knowledge entry，写 lineage 和 trust vector。
6. 市场 fan-out高价值知识自动发布 analyze/exploit/report 等后续任务。
7. 治理演化定时提升、衰减、验证、蒸馏策略和发现本体关系。

核心算法

核心实现都围绕“共享任务市场”和“知识信号循环”展开。任务是可竞争资源，知识是新的任务信号。

work_queue.py

任务市场：优先级 + 角色匹配 + 原子 claim

任务写入 agent_tasks，按 priority DESC, created_at ASC 暴露。worker 用带条件的 UPDATE ... WHERE status='pending' 抢占，多个 agent 竞争时只有一个能成功。

signal_key 对 active 任务去重，避免同一知识重复生成 pending/running 任务。

capture.py

知识捕获：先无损记录，再筛选入库

每条输出先写 raw_agent_events。随后按来源计算信号阈值：任务结果、用户纠正、错误解决、文章默认保留；普通对话需要更强信号。

入库前按内容分类 DIKW level、knowledge_type、domain、intent 和 tags。

content_hash

去重与交叉验证

完全相同内容使用 SHA-256 前缀做 content_hash 精确去重。重复内容不会创建新 entry，而是给已有知识补一条 cross_agent_validation lineage，并重置 pheromone。

fan-out

知识驱动的任务扩散

publish_tasks_for_knowledge() 根据知识类型生成后续工作。例如 vulnerability/attack 同时触发 analyst 影响分析、exploiter 授权验证和 reporter 滚动报告。

orchestrator.py

积压触发扩容

orchestrator 周期扫描 pending 任务，统计各角色 idle agent 和 active spawn。当某角色任务积压超过容量时，写入 spawn_requests，由外部 spawn handler 决定是否生成新 agent。

recovery

可恢复执行

卡在 running 的任务会被 recover_stale_work_claims() 释放回 pending；卡住的 spawn claim 也会恢复。所有状态在 SQLite 中持久化，进程重启后可以继续轮询。

知识治理与自适应

治理循环负责把一次性输出变成可复用知识，同时把过期、被反驳、低价值的路径降权。

trust = 0.4 * base_confidence
+ 0.3 * logic_soundness
+ 0.3 * cross_validation DIKW 提升同时要求 trust 和 corroborating source 数量达标：L2 需要 1 个来源和 0.60；L3 需要 2 个来源和 0.75；L4 需要 3 个来源和 0.85。

治理 tick 做什么

60s
DIKW promotion

扫描 active knowledge_entries，满足 trust 和 lineage 条件时提升 level。

60s
counter-example decay

反例超过阈值时，规则失效或知识标记 stale。

60s
validation / wisdom / ontology

验证队列、L4 wisdom 蒸馏、tag 共现本体关系发现一起运行。

15s
power schedule

按预算消耗和漏洞密度切换 breadth、balanced、depth，并让空闲 agent 抢高优先级任务。

信息素衰减

知识条目带有 pheromone 和 last_validated_at。长时间未验证时按指数衰减：默认每 6 小时乘以 0.95。低于 0.1 的条目标记为 stale。重复验证或交叉验证会 boost 并更新验证时间。

new_pheromone = old_pheromone * 0.95 ^ elapsed_intervals
if new_pheromone < 0.1:
    status = "stale"

Power schedule

调度策略借鉴 fuzzing 的预算分配思路。预算消耗低于 30% 时偏 breadth；高于 70% 时偏 depth；漏洞密度超过 15% 且预算已过探索初期时强制 depth。超过链深限制的 spawn 请求会被拒绝。

if vuln_density > 0.15 and budget_ratio > 0.3:
    strategy = "depth"
elif budget_ratio < 0.3:
    strategy = "breadth"
elif budget_ratio > 0.7:
    strategy = "depth"
else:
    strategy = "balanced"

漏洞赏金知识循环

DIKW 回答“我们知道什么”，赏金门控回答“这个候选发现是否值得提交”。两者共享 knowledge entry，但门控状态单独维护。

ROI 排序expected_payout / hours * competition_factor
PoC 存在poc_exists
干净复现clean_repro
安全影响impactful
低权限可达low_priv_reachable
范围和去重in_scope + deduplicated

全部 gate 通过后，hypothesis 变为 validated，对应知识至少提升到 L3。任一 gate 失败会写入 negative_knowledge 并生成 counter example，避免后续 campaign 重复走死路。

操作入口

外部系统通常只需要 submit/status/result；worker 和 runner 是蜂群内部执行入口。

常用命令

# 提交高层任务
python3 swarmctl.py task submit \
  --source codex \
  --task "对目标做授权范围内的侦察和初筛" \
  --intent recon \
  --target-type webapp \
  --target example.test \
  --json

# 查询状态和结果
python3 swarmctl.py task status --run-id "$RUN_ID" --json
python3 swarmctl.py task result --run-id "$RUN_ID" --json

# 管理模型画像
python3 swarmctl.py models list
python3 swarmctl.py models set --role analyst --provider claude --model sonnet --default

start_swarm.py：创建 run 并发布 seed tasks。

swarmctl.py：外部 client API、模型 profile 管理、事件和 summary。
